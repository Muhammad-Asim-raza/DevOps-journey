============================================
   ALB MONITORING AND TROUBLESHOOTING
============================================
[ CLOUDWATCH METRICS (namespace AWS/ApplicationELB, Day 64) ]
  HTTPCode_Target_5XX_Count   errors from YOUR app        -> alarm
  HTTPCode_ELB_5XX_Count      errors generated by the ALB -> alarm
  TargetResponseTime (p99)    latency                     -> alarm
  UnHealthyHostCount          per target group            -> alarm
  HealthyHostCount            capacity floor              -> alarm
  RequestCount                traffic (and ALBRequestCountPerTarget
                              for Auto Scaling tomorrow)
  RejectedConnectionCount     ALB at capacity
  Dimensions: LoadBalancer=app/NAME/ID, TargetGroup=targetgroup/NAME/ID

  Example alarm (page when the app returns errors):
  aws cloudwatch put-metric-alarm --alarm-name alb-target-5xx \
    --namespace AWS/ApplicationELB --metric-name HTTPCode_Target_5XX_Count \
    --dimensions Name=LoadBalancer,Value=app/devops-journey-alb/abc123 \
    --statistic Sum --period 60 --evaluation-periods 3 \
    --datapoints-to-alarm 2 --threshold 10 \
    --comparison-operator GreaterThanOrEqualToThreshold \
    --treat-missing-data notBreaching --alarm-actions SNS_TOPIC_ARN

[ ERROR DECODER ]
  502 Bad Gateway      target closed the connection, sent a malformed
                       response, or crashed mid-request; also protocol
                       mismatch (HTTPS to an HTTP-only target)
  503 Service Unavail. NO healthy targets, or the target group is empty
  504 Gateway Timeout  target didn't answer within idle timeout, or
                       security group/NACL blocks ALB -> target
  400 / 460 / 463      malformed request / client closed early /
                       too many X-Forwarded-For addresses
  403                  WAF block or listener rule fixed-response

[ TARGETS UNHEALTHY? CHECKLIST ]
  1. aws elbv2 describe-target-health --target-group-arn $TG
     (Reason and Description tell you why)
  2. Does the app SG allow the health-check port FROM THE ALB SG?
  3. Right port, path, protocol, and success code (matcher)?
  4. Is the app actually listening on 0.0.0.0, not 127.0.0.1?
  5. Does /health redirect (301/302) so it never returns 200?
  6. Are targets in subnets that the ALB's AZs actually cover?
  7. Container still starting? Increase health check grace
     (ECS healthCheckGracePeriodSeconds).

[ ACCESS LOGS ]
  Enable to S3, query with Athena. Fields: client IP, target IP,
  request/target processing time, status codes, bytes, user agent.
  Tells you WHICH target and how long, which CloudWatch metrics can't.
